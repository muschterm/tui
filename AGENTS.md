# AGENTS

This repository defines how to build polished, reusable terminal user interfaces in Go, Rust, and Bun. The initial example has left navigation, a central working area with an optional bottom panel, and a right sidebar for surfaces such as files and Git. Projects, threads, and agent integrations are example application concepts, not assumptions every TUI must inherit.

The project has a documented design blueprint and a first Go server/shell slice with synthetic activity; provider, collaborative-editor, Git and real embedded-terminal integrations remain incomplete. Read [README.md](README.md), [the design brief](docs/design/brief.md), and [the interview record](docs/design/interview.md) before making architectural changes. Do not turn an unanswered interview question or a research recommendation into an accepted decision.

## Instruction organization

`AGENTS.md` is the canonical source of project rules and agent guidance. Package `AGENTS.md` files add local rules. Each `CLAUDE.md` imports the adjacent `AGENTS.md`; update the canonical file rather than duplicating instructions.

## Engineering priorities

1. Protect user work: file edits, unsaved buffers, and Git operations must have explicit, predictable outcomes.
2. Make interaction coherent: every application action needs a keyboard path; pointer interaction must cover visible controls, scrolling, selection, and pane resizing where the terminal supports it.
3. Design for terminal capabilities: document a tested baseline, detect enhancements, and provide usable fallbacks. Never claim universal terminal, SSH, or tmux compatibility without evidence.
4. Keep the reusable UI independent of application-specific concepts and provider integrations.
5. Maintain a shared behavior specification and three reference apps while using idiomatic code and tooling in each language. Extract libraries when actual reuse justifies them.
6. Make quality observable through acceptance criteria, meaningful tests, visual review, and recorded compatibility checks. “Perfect” is an aspiration, not a substitute for evidence.

Build the Go reference app first with Bubble Tea v2, Bubbles, and Lip Gloss, as selected at the user's request. Rust uses Ratatui; Bun uses React + public Ink with Bun.Terminal for interactive subprocesses. Validate Bun compatibility explicitly and do not equate the public stack with Claude Code's private renderer. See [implementation sequence](docs/design/implementation.md).

## Subagents

Delegate when a subagent isolates context or runs independent, bounded work in parallel for less total cost than doing it inline. Use a direct tool call for a single lookup, and keep work in the parent when the brief would have to restate most of the parent's reasoning.

- **Brief:** give each subagent one objective, the context it needs, acceptance criteria and the files it owns. Never let two subagents edit the same file. Send a focused brief, not the whole conversation.
- **Result:** ask for a concise report: evidence or `file:line` references, checks run with their outcomes, and open issues. Do not redo delegated work in the parent.
- **Escalation:** a subagent that cannot finish returns what it found, what it tried and a recommended next step. Raise effort before changing tier, and hand completed work forward instead of restarting.
- **Ownership:** the parent owns prioritization, integration, verification and the final response. User instructions override this section.

### Model and effort

Subagents exist to do bounded work more cheaply than the parent. The parent's model (Opus 5.5 or GPT-6 Astra) orchestrates, owns architecture and difficult tradeoffs, and verifies consequential results; delegate to the cheapest tier that can finish the task, and upgrade only when it falls short.

Use only the models, identifiers and effort controls the current harness exposes, and respect explicit user selections. Prefer the parent model's family; inherit the parent model when the preferred one is unavailable, and use harness defaults when selection is unavailable. Where a harness fixes effort per agent definition rather than per call, use a defined agent type for the row you need instead of assuming the effort.

| Work | Claude | OpenAI |
| --- | --- | --- |
| Bounded retrieval, extraction, file discovery and mechanical transforms | Sonnet 5 low | GPT-6 Luna (`gpt-6-luna`) low |
| Well-scoped implementation, routine debugging, focused analysis and small self-contained tasks with clear acceptance criteria | Sonnet 5 low, then medium | GPT-6 Luna (`gpt-6-luna`) max |
| Upgrade: multi-step implementation, unclear causes, research synthesis, or work the tier above fell short on | Opus 5.5 low–medium | GPT-6 Sol (`gpt-6-sol`) high, then xhigh |
| Verification of consequential changes: data loss, duplicate writes, Git operations, queue/revision races, reconnect and recovery | Opus 5.5 medium | GPT-6 Astra (`gpt-6-astra`) medium |

Keep architecture, difficult tradeoffs and integration in the parent rather than delegating them at high effort. Escalate Sonnet 5 past medium by switching to Opus 5.5, and GPT-6 Luna past max by switching to GPT-6 Sol. Do not use Haiku or Fable 5.1 for subagents unless the user asks: Haiku's misses cost more to catch in the parent than they save, and Fable costs more than the parent it would serve.

## Architectural boundaries

The accepted [component construction rule](docs/design/components.md) and
[ADR 0008](docs/adr/0008-cell-native-component-state.md) define component variants
and independent selection, hover and keyboard-focus feedback.

- Keep layout, focus, input routing, and surface presentation separate from filesystem, Git, subprocess, and agent-provider operations.
- In the wider layout, keep pane controls reachable in the application chrome: left navigation toggle then the clickable application title (new thread in the filtered project, else the project chooser) at top-left; a centered project-icon/name `/` thread-title breadcrumb whose project part starts a new thread there; right-surface maximize/restore, center-bottom toggle, and right-panel toggle in that order at the far right, over the right host while it is visible. Maximize/restore is shown only while the right host is actually visible; its visible empty chooser supports the same geometry. Every right-host surface uses a dynamic tab with its own close icon and the shared maximize/restore control. Each non-terminal surface type is a singleton within that host: opening Git, Files, Agents, Plan, Activity or another non-terminal type again focuses its existing tab. Only Terminal can have multiple instances. An empty host starts hidden, explicitly showing it opens its chooser, and closing the last tab hides it. Hiding preserves surfaces. Terminals also remain available in the center-bottom panel, which is a tab row of that thread's terminal sessions with an add control and no title row: showing the wide panel while it has no session opens one immediately, each tab's icon slot ends its own session, and closing the last tab hides the panel. Choosing the compact Terminal column only changes presentation. Omit global content search. Provide local thread-title search followed by Project filter, Add project and New thread controls; filtering stays local to each client. Closed stays pinned above app settings, with a count only while collapsed and independent scrolling when expanded. See [layout behavior](docs/design/layout.md).
- At phone widths, use an explicit hamburger column picker for Conversation, Projects & threads, Surfaces and Terminal. Preserve the prompt and settings/actions across columns; questions, queue and activity stay in Conversation, reachable through the persistent attention bell. Keep compact selection separate from wide pane preferences, preserve drafts/sessions when switching, and never submit an invisible prompt below the supported size. See [small-screen layout](docs/design/layout.md#single-column-layouts-on-small-screens).
- Keep rendering free of filesystem writes, Git mutations, network requests, and subprocess launches. Route effects through explicit application commands and report results back into state.
- Use rounded outlines with stable interior backgrounds for the prompt, thread cards, queue group, question/approval containers and dialogs; square outlines remain available for explicit boundaries. Use single-row square fills for question tabs, surface tabs and compact actions. Rest is neutral, hover is stronger neutral, and selection uses an accent plus bold text; keyboard focus independently paints an accent mark in the cell before the control (its reserved end cap, icon padding or blank gutter) so focus never moves an icon or label, and underlines only where no such cell exists. Preserve selected treatment on hover and semantic status colors. Keep fill inside outline corner cells, separate tab-close targets and fixed navigation slots. Glyph-only icon controls have no fill: hover/focus embolden and lift muted ink, and only the glyph cell plus its trailing spill cell is interactive within its reserved slot. Use reserved bracket end cells when compact fills cannot be distinguished, preserving dimensions. Do not use pill caps or stepped block corners. Keep pane toggles unboxed. Bound retained ANSI styling during incremental row composition; invisible color codes must not grow with repeated painting.
- Keep questions, approvals and failures in other threads discoverable through thread badges and a persistent top-bar attention indicator, including when navigation is hidden. Explicit activation opens the relevant item; incoming events never steal focus. Use a bell with a count badge for pending items and a neutral bell without a zero badge otherwise. Keep it separate from the ordered pane controls, at the center pane's right edge: beside the visible controls while the right host is hidden, and left of the host's span while it is shown; a hidden maximize control leaves no reserved gap.
- Each reference is a complete native server and TUI. One background server per user/application manages projects, agents, queues, Git/filesystem operations, and interactive subprocesses. Multiple clients connect through authenticated loopback HTTP/WebSocket; remote access uses SSH forwarding. TUI exit leaves work running; explicit server stop gracefully cancels owned work and processes. Keep frontend-local focus/scroll/selection separate from authoritative execution state. See [server design](docs/design/server.md).
- Preserve application state in an application-specific user-home directory with an application-specific environment override, using SQLite wherever practical and auxiliary files where necessary. The server writes authoritative storage; clients use its contract. All executable/home/prefix examples are placeholders. See [storage](docs/design/storage.md).
- Model application concepts outside the reusable shell. A project/thread example must not require all consumers to adopt projects or threads.
- Restore each thread's open surfaces, prompt draft and reading position when switching back. Files/Git follow its checkout; existing terminals retain their shell sessions and working directories without restart, redirection or controller transfer. Keep workspace geometry preferences and other clients' navigation independent. See [thread restoration](docs/design/layout.md#switching-threads-and-projects).
- Threads support Close/Reopen and separate permanent Delete. Closed replaces Recents. Group each thread's title and metadata in one rounded, padded card, separated from adjacent threads, with consistent whole-card hover/focus feedback. Use a square-and-pencil New thread icon in the navigation header, retaining descriptive help and keyboard access. Navigation threads use a pulsing blue working circle, yellow/orange attention circle, red error circle, or solid green finished/idle circle. Errors take precedence over attention, then working; unknown/disconnected states remain neutral. Keep the leading status circle visible on hover/focus. Finished, closable rows show a Close check in a reserved action slot directly left of the vertical ellipsis. Closed rows are dimmed, single-content-row cards: trash uses the same reserved slot and a hover/focus-revealed Reopen icon replaces the ellipsis; the Closed heading is dimmed too. Keep that slot and title geometry stable when the action is hidden, with separate selection, lifecycle and menu targets and keyboard paths. Close preserves work and views; the current prototype permits it only without active work or pending requests. Selecting Closed reads without reopening and retains the composer with a closed banner and separate Reopen action. Explicit Reopen sends nothing; valid Send atomically reopens and accepts the prompt under the lifecycle revision guard. Delete requires an explicit confirmation and removes thread-owned live records, including saved views and command payloads, without deleting checkout files. Retain minimal retry fingerprints to prevent deleted creation retries from resurrecting threads. See [thread lifecycle](docs/design/threads.md) and [project selection](docs/design/projects.md).
- Use **thread** for the ADE's user-facing interaction entity, with one chosen agent per thread. Handoffs and agent switching are deferred. Preserve literal upstream protocol names such as ACP `session/*`; upstream session lifecycle and restoration remain distinct implementation concerns.
- Use stable ACP v1 at the application server's agent boundary; frontends retain the application's HTTP/WebSocket contract. Connect to native ACP implementations directly and adapt official local provider runtimes otherwise. Our Go adapters host installed `claude -p` and official `codex app-server` directly. Keep provider-specific translation outside generic surfaces; use the completed existing-adapter comparison as reference evidence. The user selected in-house Go adapter ownership to avoid separate installations; [ADR 0016](docs/adr/0016-built-in-go-acp-bridges.md) packages them inside the Go binary with serialized ACP pipes and directly owned official CLI children. See [ADR 0014](docs/adr/0014-acp-boundary-official-agent-runtimes.md) and the [current agent handoff](docs/implementation/agent-integration-handoff.md).
- Always use the user's installed Claude/Codex CLI, automatically discovered on the server's PATH and explicitly passed to the adapter. Optional local executable overrides must be validated. Never fall back to bundled provider runtimes or download another copy when the local CLI is missing; report unavailable. ACP adapters translate protocols, not installation ownership.
- Adapter ownership is now selected: implement our own Go ACP bridges around installed `claude -p` and `codex app-server`, delivered with the application. Do not require separate npm/Node ACP adapter or Agent SDK sidecar installations. Earlier adapter-reuse recommendations are superseded; preserve the current prototype and its evidence until replacement. Keep ACP, the unified question contract, native approval semantics and truthful delivery/recovery states. See the latest [handoff](docs/implementation/agent-integration-handoff.md).
- Support removable prompt context attachments for files, selected lines, images, Git diffs and terminal output. Capture their content at Send and preserve the accepted snapshots through queuing and recovery; later source changes must not silently alter attached content. See [prompt context](docs/design/activity.md#prompt-context-attachments).
- New thread always offers a searchable project destination and Add project, even with a project filter or only one project. Folder typeahead begins at app General's server-owned Project starting folder (home by default); registering a folder never creates disk directories. Inline `@` completion begins in the draft project or thread checkout, browses directories and adds removable file context without Send. Keep queries asynchronous, bounded and isolated from changed inputs/destinations; capture selected files server-side at Send. See [projects](docs/design/projects.md) and [file mentions](docs/design/activity.md#inline-file-mentions).
- Ordinary text pastes into the prompt; pasted images/copied files become context attachments with thumbnails where supported. Attachment inspection uses a centered, always read-only viewer with expand/restore; Markdown has raw/preview modes and an eyeball preview control. Keep it distinct from the editable Files surface, preserve drafts and focus, and distinguish clipboard intake, preview rendering and agent input capabilities. See [clipboard and previews](docs/design/activity.md#clipboard-intake-and-read-only-previews).
- New thread opens a persistent client-local per-project draft, with no authoritative thread until first valid Send atomically creates it and accepts the captured prompt. Choose the agent, then explicitly select a supported model and validate effort, permissions, context capacity and speed tier. The fixture presets Demo Agent and offers only Reference model; never invent selectable provider models. Keep selected and effective running settings available at the bottom of the prompt box, using progressive overflow when narrow; do not infer enforcement or options from names alone. See [thread configuration](docs/design/thread-configuration.md).
- Capture each prompt's selected model, effort, permissions and applicable context/speed settings at Send. During active work, including waiting, settings and overflow controls are read-only and show/use effective running values for Send; preserve and restore the editable idle preference. Idle composer changes affect future submissions; queued items keep their recorded settings unless explicitly edited. Validate and apply each item's selection before dispatch, distinguish acknowledged effective values, and preserve settings through recovery. See [per-prompt settings](docs/design/thread-configuration.md#settings-captured-per-prompt).
- Offer explicit Steer on queued messages, targeting the same active turn through a verified agent capability. Ordinary Send still queues during work. Preserve captured text, attachments and settings; bind delivery to prompt/revision and turn identity, reconcile uncertain delivery before normal dispatch, and deduplicate retries. Never substitute Stop-and-Send, a new turn, question answers or implicit Resume. Explain unsupported states and incompatible settings while retaining queued input and drafts. See [steering](docs/design/activity.md#steering-a-queued-message) and [ADR 0009](docs/adr/0009-turn-bound-steering.md).
- Show server-authoritative read-only checkout/branch context below composer controls, refreshing on selection or explicit refresh and distinguishing non-Git, detached, fixture and unavailable states. Never mutate Git to populate it. Use the existing project checkout by default and offer worktrees explicitly. Do not create an isolated worktree merely because a thread was started. Queue write-capable thread work and conflict-resolution jobs per checkout; delegated children belong to the owning run. Independent worktrees may proceed concurrently. See [workspace contract](docs/design/workspaces.md).
- Negotiate protocol versions and capabilities. Unsupported agent features must have an honest unavailable state; shared protocol framing does not establish feature parity, portable session history, or filesystem isolation.
- Keep the ADE usage display available. Populate context occupancy/capacity, applicable subscription windows, and API cost from supplied agent telemetry; preserve source, scope, units, freshness, and whether amounts are cumulative or incremental. Do not fetch external quota/pricing data or invent missing measurements. See [usage display](docs/design/usage.md).
- Keep a fixed area immediately above the prompt, outside transcript scrolling, with one Agents summary, a compact Plan summary and pending requests. Show “Agents N”, where N is the total number of children in the represented group, including completed children, with a pulsing blue circle for established active work. The count stays visible as children finish and after all have completed; it is not the remaining working count. Only when every child has successfully completed, use a solid green circle; retain the summary until explicitly dismissed. On hover or keyboard focus, the completed circle becomes an X in the same leading icon slot. Only that slot dismisses; the label still opens history. Keep the working count and full state in hover/focus help and the inspector. Never offer dismissal while work is unfinished. Activating the summary opens the singleton Agents surface, where individual children and full available history remain accessible. Plan uses completed/total progress (n/N), the same blue working and solid green all-completed states, and the same completed-only dismissal. Failed, interrupted, waiting, stale and unknown states stay distinct and never imply success. Dismissal belongs to the frontend thread view; new work or a changed group/plan reopens its summary, while unrelated stream updates do not. Keep provider histories and source truncation explicit; subagent inspection never switches the thread's agent. Pin negotiated extension dialects rather than assuming core ACP v1 supplies every child feature. See [activity presentation](docs/design/activity.md).
- When space is tight, keep compact Agents and Plan summaries and one scrollable question/approval card at a time. Preserve the prompt, request actions and drafts, with settings and usage available through the responsive footer; individual children remain accessible in Agents. The grouped summaries supersede the former running-child chips and More menu.
- Show pending questions above the prompt without replacing its draft or settings. Multi-question requests use individually filled top tabs and filled Back/Next arrows in fixed reserved slots. Hide an unavailable end arrow without giving its space to tabs. Keep a contiguous visible group containing the current question and reveal pages as navigation advances; offer a question menu only for overflow. Answered markers must not shift the header. Use separate explicit submission. Single-choice selection advances to the next question when present; checkbox selections stay on the current question. Place vertical choices and supported free text in a bounded, scrollable question container. Support blocking and continued-work asynchronous requests through verified integration capabilities. Answers target the server-owned request identity and revision, not the ordinary prompt queue; reconnect, navigation and defaults never submit answers. See [question behavior](docs/design/questions.md).
- After confirmed question resolution, preserve one compact read-only Answered Q&A card in the transcript, with original questions, accepted answers and overflow-only expansion. Keep pending/failed delivery distinct, preserve response identity and chronology across clients/recovery, and never turn history inspection into resubmission. See [answered history](docs/design/questions.md#answered-questions-in-conversation-history).
- Standardize questions and answers in the application, with one frontend contract and server-owned adapter routing. Prefer native structured responses; an explicitly supported structured-text fallback may end the agent turn and deliver the answer through a correlated new turn. It remains an answer to the original request, never an ordinary frontend prompt or a claimed asynchronous response. Preserve explicit Submit, queue/writer scheduling, captured settings and Resume gates. Keep approvals distinct and never convert failed native delivery into a new prompt implicitly. See [ADR 0015](docs/adr/0015-app-owned-question-contract.md).
- An interactive PTY supplies bytes and process I/O, not pane rendering. Keep child terminal emulation and input routing bounded to its surface, and keep ACP protocol stdio separate from PTYs. Each server-owned terminal has one explicit input/resize controller even when several clients observe it.
- Closing a right Terminal tab ends its server session. The bottom terminal also has an explicit session-close control; pane toggles only hide/show and preserve sessions. Notify other observers when a session ends, reject stale input/resize, and distinguish accepted close from confirmed process exit. Reopening a closed terminal creates a new session. See [terminal lifecycle](docs/design/layout.md#terminal-close-and-panel-hide).
- Present permission requests as distinct approval cards above the prompt, showing the action, supplied files/location and agent-supported choices. Open full details in Activity, preserve prompt drafts, and keep approval scope and request identity explicit. See [approval cards](docs/design/activity.md#approval-cards).
- Treat terminal features as negotiated capabilities, not facts inferred solely from a terminal name or environment variable. When an explicit action is unavailable, show a brief, non-blocking, auto-dismissing notice with a useful fallback where possible; preserve focus and work, coalesce repeated notices, and keep unresolved data/save errors visible at their source. See [unavailable terminal features](docs/design/layout.md#unavailable-terminal-features).
- Keep terminal color capability local to the connected TUI. Respect nonempty `NO_COLOR`, retain deliberate neutral 256/16-color surfaces when true color is unconfirmed, and never force RGB merely because SSH or a terminal name is present. Gate optional color queries against known parser support, preserve typing during bounded reply reassembly, and keep message alignment independent of palette equality. See [color compatibility evidence](docs/research/go-colors-2026-09-20.md).
- Keep current working-tree, staged, and branch diffs distinct from the recorded start/end comparison labelled changes observed during a turn. Show provider-reported edits separately where available; external edits can contribute to the observation. Automatic rollback is deferred.
- Choose concrete package boundaries, persistence, and integration contracts only after their design decisions are settled. Record consequential tradeoffs in ADRs; record ordinary behavior in the specification.

- Show Thinking for reported running turns and a distinct Waiting status while waiting; clear activity on terminal outcomes and do not infer hidden reasoning. Stop labels interrupt/cancel and is available only for active turns, including waiting. Send is a blue circle at the far right; Stop is a red circle directly left when active; paperclip sits left of Stop or Send, with the context gauge to its left. Preserve footer and keyboard access while maximizing.
- Inset the prompt and footer controls from pane edges. Place selected agent/model/settings at the left and usage/attachment/Stop/Send controls at the right of the same row; progressively move lower-priority controls into a vertical ellipsis as width decreases, keeping Send, active Stop and the model longest. Use one row, with the settings ellipsis directly after the remaining left-aligned fields. Usage has a separate ellipsis at the far left of the right-aligned action group and opens full context/percentage, billing and cost details. Restore controls as it widens and preserve access to hidden settings and recovery actions. Outline the typing area clearly, with the settings/actions row outside and below its border. Center close glyphs in their hit areas, preserving separate close and label actions. See [composer refinement](docs/design/layout.md#controls-and-composer-refinement-2026-09-19).

- Settings uses the left sidebar for categories and replaces all main workspace panes/composer with the selected configuration. Back restores pane geometry, surfaces, terminal associations, reading positions and drafts; hidden composer input must not activate. Keep the attention bell available. Compact settings switches categories/form through hamburger/F2. See [settings](docs/design/settings.md).
- Keep settings category and scope separate. App gear offers General, Appearance, Keybindings and About with `Settings / <category>`; project gear offers only Project, General and Keybindings for one named project with `Settings / <category> / <name>`. All projects is never a settings project scope. Project contains only Name, Icon and Remove, with badge color inside Icon. Project General owns the inherited/overridden workspace default and Use app default reset through revisioned `project.update`; restart continuation stays app-only. Project Keybindings reports inherited app bindings and unavailable overrides until implemented. No project Appearance or theme shortcut may change app theme while project settings is visible. See [settings](docs/design/settings.md).
- Keep app execution defaults server-owned and revisioned; projects inherit or explicitly override the workspace default. Saving preferences never moves existing threads. Reject unsupported worktree creation. Project removal requires a project/revision/count-specific confirmation, deletes its threads and retained application payloads, and preserves disk files; active work blocks removal. Re-registering a removed folder has a new identity. See [settings](docs/design/settings.md) and [project removal](docs/design/projects.md#sidebar-and-project-settings-refinement--2026-09-20).

## Working Style

- Assume technical fluency — skip explanations of basic concepts (TypeScript, Cloudflare Workers, REST, SQL) unless explicitly asked.
- Prefer concise, structured responses over verbose prose.
- Raise concerns before writing code. Wrong architectural calls are cheaper to catch early than to refactor later.
- Prefer small vertical slices over broad scaffolding. Explain the benefit and cost of new dependencies before adding them.
- Git commits: imperative one-liner subject, optional short markdown body for context. No co-author trailers or generated-by footers.
- Git operations while developing this repository: never push and never pull from a remote; committing locally only. The future Git client's pull/rebase features are product requirements, not permission to perform remote Git operations during repository work.

Before implementation, inspect relevant code, tests, documentation, and scoped instructions. Record assumptions and unresolved ambiguities in the task notes or planning artifacts. Verify uncertain terminal and library behavior against versioned upstream documentation and actual terminal checks; distinguish documented support from behavior verified in this project.

Before completing an implementation change, run applicable formatting checks, builds, and relevant tests using the configured tooling. Review the diff for data-loss and duplicate-write risks. Report changes, validation, and remaining risks; record consequential architectural changes in ADRs and keep related documentation current. For documentation-only work, verify consistency and the diff without inventing unavailable build or test commands.

## Shared coding standards

- Build each reference app CLI-first: one binary whose default command opens the TUI, with conventional subcommands, `--help` on every command, shell completion, a version command, stable exit codes (0 success, 1 failure, 2 usage) and script-friendly JSON for status and diagnostics. Keep parsing, help and exit codes in one testable package, and keep non-Go validation tooling out of Go package directories. See [ADR 0012](docs/adr/0012-go-cli-framework.md).
- Use explicit state transitions and typed events. Keep background work cancellable, bound queues and retained output, and avoid blocking input/rendering on I/O.
- Keep prompt queues distinct from checkout writer queues. A frontend reconnect must catch up without resubmitting prompts, rerunning tool calls, or repeating Git/file mutations. Use an application command identity and coherent snapshot/update boundary; detailed messages and transaction boundaries require implementation design. After server restart, restore preserved state and require explicit Resume by default. Allow explicitly opted-in continuation only for execution integrations with verified recovery eligibility; manual Stop and pending questions/approvals remain gated. Store this setting per server environment and capability-gate it. Attaching to a running server only catches up. See [settings](docs/design/settings.md).
- Route keyboard and mouse activation through the same application commands. Define focus, hit testing, modal precedence, scrolling, and resize behavior in the shared specification before implementing competing conventions.
- Expose edit, remove and reorder actions directly in each thread's visible prompt queue until execution starts. Reconcile queue revisions and dispatch races on the server; preserve unsent edits and unchanged attachment captures. Queue changes do not interrupt active work, bypass checkout scheduling or resume saved execution. See [queue controls](docs/design/activity.md#prompt-queue-controls).
- Combine Codex's workspace composition with the richer color, icons, media, and role hierarchy requested through Omarchy/herdr examples. Distinguish user messages, agent replies, tools/MCP, and subagents through coordinated colors, labels, and structure. Use kitty image placements for the rich experience when supported; keep an intentionally styled fallback. Square corners are acceptable. Use [visual references](docs/design/visual-design.md) and actual interactive review; a collection of boxed widgets is not sufficient evidence of polish.
- Keep ordinary activity compact and open full detail in an inspector. Avoid nested boxes and repetitive dropdown chevrons; setting values remain visible and individually reachable. Use consistent control icons, verified official agent artwork and clean user labels, not invented avatars or approximate vendor logos. SVG sources rasterize to cached PNG/pixels for kitty; keep product/provider/model identities distinct and record asset provenance. See [icon and graphics guidance](docs/design/visual-design.md).
- Keep ordinary conversation messages free of repeated You/Agent headers; alignment and tint distinguish their roles. Keep meaningful tool/MCP and detail labels. Keep UI copy functional: omit captions that merely explain adjacent values or output, including “Running with selected settings.” Show matching selected/running settings once; label mismatches, errors, stale data and other meaningful distinctions. Keep mockup disclaimers outside the depicted product. Activity rows use full-row activation with hover/focus feedback, without repeated pane-like inspector icons.
- Use the inspected [T3 Code design reference](docs/research/t3-code-design.md) for stable pane toggles, opened-surface lifecycle, compact composer controls and SVG identity assets. Translate these into terminal cells; T3's feature inventory, bindings and implementation rules do not replace this project's accepted specification.
- Use recognizable Nerd Font control icons with distinct pane open/closed states and an explicit plain-symbol fallback. Tabs show type icon plus name; hover/focus reveals close only in the icon slot. Overflow appears only for hidden tabs and lists each surface once. Enter sends from the composer; Shift+Enter inserts a newline (Ctrl+J fallback). Let the composer grow to a bounded height before scrolling, and show scrollbars where content overflows. See [the implementation-review refinement](docs/design/layout.md#controls-and-composer-refinement-2026-09-19).
- Use terminal cell widths and grapheme-aware text operations. Do not assume bytes, code points, and displayed columns are interchangeable. Review Unicode, narrow layouts, and long paths.
- Restore terminal state on normal exit, cancellation, and recoverable failure. Exercise resize and suspend/resume behavior on supported platforms.
- Never treat untrusted file contents, subprocess output, or repository text as safe terminal control sequences. Handle styling and terminal escape sequences deliberately.
- File saves must account for concurrent changes and failure without silently destroying the original. Make overwrite, discard, and destructive Git actions explicit; do not introduce automatic staging, commits, or remote operations as a side effect of viewing a surface.
- File editing supports simultaneous clients, live changes and cursor presence, prompt autosave, and undo of each client’s own edits. Merge clean external changes; preserve versions and pause autosave for overlap, deletion, or replacement until reviewed. Preserve acknowledged edits across reconnects and distinguish document durability from disk-save success. See [the editor contract](docs/design/editor.md).
- Graph actions must identify the selected commit and the branch/HEAD they affect. The Git client's default Pull must enforce fast-forward-only integration; a failure must not silently fall back to merge or rebase.
- Before application-managed Git operations that rewrite files, finish pending saves, pause disk autosave during the operation, and reconcile open buffers before resuming. Preserve edits and stop for review on save/reconciliation failure; stale saves must not overwrite Git's resulting files. See [Git/buffer coordination](docs/design/git-client.md#coordinating-git-with-live-buffers).
- Treat merge/rebase progress as explicit application state. “Resolve with agent” may edit conflicted files and run relevant checks, then must stop for user review before staging resolutions or continuing the operation. This is the user's corrected Q10 decision. Preserve unrelated work and expose progress, cancellation, and failures; do not substitute skip, discard, or unrelated Git actions for successful resolution.
- Share observable behavior and test scenarios across languages; do not force identical internal abstractions or dependencies.
