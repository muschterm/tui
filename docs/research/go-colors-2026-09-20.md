# Go color compatibility — 2026-09-20

The user's Omarchy/SSH photo showed saturated blue question/composer backgrounds
and cyan selection. Setting `COLORTERM=truecolor` improved the live rendering.
This supports a capability-detection diagnosis; the exact terminal, version,
remote environment and any tmux configuration were not captured. The user accepted
automatic detection where supported and a more readable limited-color fallback.

## Implementation and tradeoffs

- Keep Bubble Tea's environment/terminfo/tmux startup detection. Start the cached
  frame with neutral surfaces until its profile message arrives. Store capability
  state only in the connected model, independently of server reconnects and saved
  client views.
- For ANSI/ANSI256 only, send one XTVERSION request. A recognized Ghostty, kitty or
  iTerm2 reply permits separate RGB and Tc queries. Only a positive capability
  response upgrades the renderer. A terminal name alone never upgrades it. There
  is no retry loop, startup wait or tmux passthrough; unanswered queries retain the
  fallback. Skip known Apple Terminal and already-detected true color.
- Normalize the verified iTerm2 `RGB=8` reply before Bubble Tea's internal handler;
  v2.0.9 otherwise recognizes only bare `RGB` and `Tc`. Reject unsolicited color
  upgrades. Honor every nonempty `NO_COLOR`, including `0` and `false`; the pinned
  colorprofile implementation otherwise interprets it as a Boolean.
- Use explicit neutral 256/16-color surfaces in both themes. Keep accents in small
  controls and indicators. Indexed blue pulses use brightness steps. In 16-color
  mode, hovered controls use neutral text for contrast. Avoid OSC default-color
  writes in limited-color/monochrome modes, since those bypass SGR downsampling.
- Keep transcript alignment explicit. The old renderer inferred user alignment
  from the background color, which incorrectly moved agent replies when fallback
  input and canvas colors were equal. Palette changes now preserve the same
  visible text, wrapping and alignment.

No dependency version changed. colorprofile v0.4.3 and Ultraviolet
v0.0.0-20260811164956-006e29f97886 move from indirect to direct imports for the
existing runtime's profile/event types and decoder. There is no additional
download, native requirement or distribution dependency. This is a reversible
compatibility layer, with no storage/protocol or architectural boundary change.

## Fragmented replies

An actual PTY test exposed the pinned Ultraviolet reader's 50 ms escape timeout:
a Tc response split after its DCS header could expire and put its remaining hex
digits in the draft. The client now reassembles only recognized, incomplete
XTVERSION/XTGETTCAP response headers from its own outstanding probes. It retains
at most 512 bytes, uses a one-second absolute deadline, and decodes a complete
response using the same pinned decoder. Success/negative replies do not become
prompt input. Timers carry identities, so an old expiry cannot clear a new reply.

Once an upstream decoder has split a response, printable response bytes and user
typing are ambiguous. On timeout, overflow, malformed content or unrelated input,
replay retained key events before the user's next action; never silently discard
typing or defer Ctrl+Q. Framework messages still pass through Bubble Tea's own
event loop. This bounds the workaround rather than claiming arbitrary stream
recovery. Splits before a recognizable header or inside the terminator remain an
upstream compatibility gap. A reply exceeding the reconstruction bound may leave
unclassified printable bytes as input. No universal SSH fragmentation guarantee
is claimed; a future input-reader fix can replace this compatibility layer.

## Primary-source checks

Inspected pinned local sources:

- [Bubble Tea v2.0.9 termcap.go](https://github.com/charmbracelet/bubbletea/blob/v2.0.9/termcap.go):
  capability commands and the warning about corrupt output in Apple Terminal.
- [Bubble Tea v2.0.9 tea.go](https://github.com/charmbracelet/bubbletea/blob/v2.0.9/tea.go):
  internal RGB/Tc upgrade before model delivery and ColorProfileMsg publication.
- [colorprofile v0.4.3 env.go](https://github.com/charmbracelet/colorprofile/blob/v0.4.3/env.go):
  environment/terminfo/tmux detection and Boolean NO_COLOR handling.
- [Ultraviolet terminal_reader.go](https://github.com/charmbracelet/ultraviolet/blob/006e29f97886/terminal_reader.go):
  50 ms default and incomplete-sequence expiry; its decoder validates successful
  XTGETTCAP responses and decodes their hex payloads.

Official current branches inspected on this date, **not pinned release/runtime
verification**:

- [Ghostty responses](https://github.com/ghostty-org/ghostty/blob/main/src/termio/stream_handler.zig)
  and [Tc capability](https://github.com/ghostty-org/ghostty/blob/main/src/terminfo/ghostty.zig).
- [kitty version](https://github.com/kovidgoyal/kitty/blob/master/kitty/screen.c)
  and [boolean capability replies](https://github.com/kovidgoyal/kitty/blob/master/kitty/terminfo.py).
- iTerm2 [XTVERSION parser](https://github.com/gnachman/iTerm2/blob/master/sources/VT100/VT100CSIParser.m),
  [version reply](https://github.com/gnachman/iTerm2/blob/master/sources/VT100/VT100Output.m),
  and [RGB=8 reply](https://github.com/gnachman/iTerm2/blob/master/sources/VT100/VT100Terminal.m).
- [tmux 3.5a input parser](https://github.com/tmux/tmux/blob/3.5a/input.c) was not
  found to supply these capability replies; no assumption of passthrough is made.
- [Alacritty handler](https://github.com/alacritty/alacritty/blob/master/alacritty_terminal/src/term/mod.rs)
  did not establish the queried enhancements. Generic TERM without COLORTERM can
  therefore retain fallback, even when its local terminal supports true color.
- [Ghostty SSH documentation](https://ghostty.org/docs/features/ssh) explains that
  COLORTERM forwarding depends on SSH server AcceptEnv. No host settings changed.

- `GOCACHE=/tmp/tui-go-build make check`: formatting, vet, all race tests and native
  build pass. Tests cover one-shot negotiation, numeric/invalid/unsolicited replies,
  NO_COLOR, fallback surfaces, transcript identity, cached input restyling, draft/
  focus/reading preservation, bounded reassembly, input replay and framework events.
- `python3 scripts/pty_colors.py --artifacts /private/tmp/tui-color-pty-final`:
  native binary and isolated server with synthetic responses. Scenarios include
  silent 256/16 colors, Ghostty/kitty/iTerm2 positive replies, negative replies,
  unknown/tmux responders, Apple veto, NO_COLOR, and existing true-color detection.
  Exercise 80 ms fragmented version/capability replies, normal typing after replies,
  abandoned-response expiry and Ctrl+Q. See the [recorded report](go-color-captures/color-pty-report.json).
- `python3 scripts/pty_smoke.py --artifacts /private/tmp/tui-color-smoke`: all 29
  existing input, lifecycle, question, mouse/resize and terminal-cleanup checks pass.
  See the [recorded report](go-color-captures/shell-pty-report.json).
- Six actual View captures cover both themes in true color, 256 and 16 colors;
  [capture notes](go-color-captures/README.md) distinguish static rendering from
  actual terminal screenshots. Neutral fallbacks and message alignment reviewed.

No actual Ghostty, iTerm2, kitty, Alacritty, SSH or tmux end-to-end session was run
for this change. Test responder names/version strings are fixtures, not evidence
that those installed terminal versions were tested. The user's successful manual
COLORTERM workaround is separate live feedback. No user server was stopped and no
Git pull, push, staging or commit occurred.
