## What changed

**Agent records (`internal/tui/agents.go`, new).** Agents are resolved from
`Snapshot.Agents` by `Thread.AgentID`, then by the legacy `Thread.Agent` value,
so pre-existing fixture threads named `Fixture agent` keep working. `agentConfig`
holds the option catalogue in effect for a thread: `Thread.Options` when the live
session has published one, otherwise the probe-time `Agent.Options`. The
catalogue is read from the snapshot on each use and never cached in client
state, because a model change can add or remove options mid-session. Readiness
(`ready`, `unprobed`, `probing`, `unauthenticated`, `unavailable`, unknown) and
`Detail` come from the record; nothing is inferred from an agent's name.

**Composer menus (`prompt_settings.go`).** With capability `acp-agents` and at
least one record, the agent field lists every configured agent with its
readiness and truncated detail, plus `Probe`/`Refresh options` for the chosen
ACP agent and an `Agent defaults…` entry. Model/effort/permissions/context/speed
menus are built from that field's option (`Agent.Fields` → option ID → values),
marking the current value and showing `ConfigValue.Description` as the row's
help. A field with no option shows one fixed `Agent default …` entry; an
unprobed agent shows `No probed options` plus the probe action. Unmapped options
appear read-only in the defaults menu as opaque agent defaults. Labels prefer
`ConfigValue.Name` and fall back to the existing `settings_display.go` tables.
Servers without agent records keep the previous fixture menus verbatim.

**Selection and validation.** `setting-agent` binds a per-project draft to an
agent ID and resets dependent settings to that catalogue's `Current` values;
an authoritative thread refuses the change and says so (one agent per thread).
`setting-field` captures option **value IDs**, and a model change re-resolves the
other fields, keeping values the catalogue still offers. `sendBlocked` now
delegates to `agentSendBlocked`: unready agents block with their readiness
reason, ACP agents validate each mapped field against its option, the fixture
agent keeps its existing fixed-option rule, and a server without `acp-agents`
keeps the previous "not connected yet" message, accepting either the legacy
`Fixture agent` value or a published fixture agent record. `thread.start` carries the agent
ID (or the legacy value when no record resolves). `agent.probe` is gated on
capability `agent-probe` and carries `TargetID` plus the draft/thread project.

**Thread presentation.** `Role: "thought"` rows render muted under a single
`Thinking` label with muted body text; tool/MCP rows keep their existing styling
and `· state` suffix for pending/running/completed/failed. `Thread.State =
"failed"` adds a non-dismissible `Failed · <Error>` status entry with a red
indicator to the fixed strip above the prompt; Send stays available and Stop
does not appear. A finished turn whose `StopReason` is not `end_turn` appends one
gold status line at the end of the transcript. `Delivery` is labelled
confirmed/unconfirmed in the Activity surface, with `acp-delivered` treated like
the fixture values. Approval cards already render agent `Choices` as buttons in
the agent's own order with the detail above them and a scrolling body; Resume,
Stop and the Agents/Plan/Activity surfaces are unchanged and behave with empty
`Children`.

**Usage.** `Thread.Usage` now feeds the composer gauge, its hover help, the usage
menu and the Activity usage page: used, capacity, percentage, source and
reported-at. Missing or incoherent telemetry (`Size <= 0`) stays `unavailable`;
no amount, percentage, cost or quota window is derived.

## T3 Code findings used

- `apps/web/src/components/chat/ModelListRow.tsx`,
  `ProviderModelPicker.tsx`, `ModelPickerContent.tsx`: per-entry readiness is an
  inline badge beside the name, the trigger repeats the unavailable state, and
  providers needing setup get a status sentence plus an explicit action row.
  Translated to a cell UI as `Name · state · detail` per menu row and a separate
  probe row, rather than a disabled row with a tooltip.
- `ProviderStatusBanner.tsx` status vocabulary ("Sign in via the CLI to
  authenticate again.", "No models are available for this provider.") shaped the
  readiness sentences in `agentUnready`.
- T3 has **no** probe or refresh action: its provider status is pushed by the
  server. This slice's options come from an explicit `agent.probe`, so the probe
  row is a deliberate divergence, not a translation.
- `MessagesTimeline.tsx` `ReasoningTimelineRow`: reasoning is muted, labelled
  `Thinking` while live and `Thought` once settled, and is context rather than
  the answer. The muted single-label treatment is adopted; the settled `Thought`
  wording is not, because the checkpoint specifies `Thinking`.
- `ComposerPendingApprovalPanel.tsx` / `ComposerPendingApprovalActions.tsx`:
  detail sits above the buttons, with extra options in an overflow menu. Matches
  the existing card. T3 orders deny before allow and promotes allow; this slice
  keeps the agent's own `Choices` order, because the answer carries the chosen
  name and reordering would misstate the agent's offer.
- `ThreadErrorBanner.tsx`: an error is a dismissible banner and the composer is
  never disabled by it. Adopted for `State = "failed"` except dismissal, which is
  not implemented here.
- Stop reasons have no dedicated T3 UI (`packages/contracts/src/providerRuntime.ts`
  defines the strings; adapters fold them into the error banner or a warning
  row), so the one-line transcript status is this project's own wording.

Recorded adapter streams in `docs/research/acp-fixtures/` were read for realistic

## Limits

- No live terminal review was performed: every result above comes from unit
  tests and in-process frame captures. Nothing here is evidence that the menus,
  gauge or status rows look right in a real terminal, under a Nerd Font, or over
  SSH/tmux.
- No live agent was contacted from the TUI. Agent records, options, usage and
  approval requests in tests are handwritten values shaped by the recorded
  streams, not a live session.
- The failure status entry is not dismissible and has no retry affordance beyond
  Send.
- Boolean options are rendered as ordinary two-value selects; no dedicated
  toggle presentation exists yet.
- Thread-level `Effective` values are shown through the existing read-only
  locked-composer path and were not re-verified against a live
  `set_config_option` response.
