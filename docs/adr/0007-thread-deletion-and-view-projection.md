# Delete thread payloads while preserving retry safety

Thread deletion removes its authoritative state, owned terminal fixtures, stored command payloads and all clients' saved thread views in one SQLite transaction. The server projects subsequent view writes onto live thread identities so a stale client cannot restore deleted drafts; view revision checks still protect unrelated client changes. This gives up completely opaque view storage: the server understands only thread ownership fields and preserves other values. See [thread lifecycle](../design/threads.md).

Retain only command identity, SHA-256 fingerprint and a minimal receipt for the deletion and the original creation command. Deleting the creation identity as well would let a lost-ack retry recreate the thread; retaining its original payload would keep the deleted title and settings. Other thread command payloads are removed. Retrying the deleted creation returns `deleted` with no target identity. This is logical deletion from live application records, not forensic erasure of SQLite journals, recovery exports or external backups. The first slice has synthetic work; real process/provider teardown must establish an explicit outcome before publishing completed deletion.
