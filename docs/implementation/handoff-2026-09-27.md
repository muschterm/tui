## User decisions recorded this session

All recorded 2026-09-26, carried into ADR 0026/0027 and
[git-client.md, Pull and integration](../design/git-client.md#pull-and-integration):

- **`exec` lines are not supported.** A plan naming any other action than
  the confirmed parity set (`pick`, `reword`, `edit`, `squash`, `fixup`,
  `fixup -C`, `fixup -c`, `drop`, `break`, reordering) is invalid.
- **Merge commits in the rewritten range are flattened with a warning.**
  The plan read flags them; starting needs an explicit acknowledgement, and
  the confirmation must say the merges will be dropped and their side
  commits replayed linearly (`--rebase-merges` is never used).
- **Cherry-pick and revert are deferred.**
- **`--update-refs` is a per-plan toggle, default off.** The plan read
  lists the local branches that would move, so the confirmation can name
  them before the toggle is turned on.

## Orchestrator engineering decisions (reversible; recorded in ADR 0026/0027)

- Honour the user's Git configuration for signing, hooks and identity on
  application rebases exactly as for other writes (ADR 0020/0021); only
  configuration that would change the plan's meaning is neutralised on the
  command line (autosquash, autostash, update-refs, rebase-merges,
  fork-point, rescheduleFailedExec, `rebase.backend=merge`,
  `missingCommitsCheck=error`, `abbreviateCommands=false`,
  `instructionFormat=%s`, `commit.cleanup=verbatim`, `commit.verbose=false`).
- **rerere is disabled** for application rebases; no preimage is recorded
  or replayed.
- **Edit modes:** `reset` (Sublime Merge's "edit commit contents") is the
  default — the server soft-resets to the parent as soon as Git stops, so
  changes are staged and can be split; `amend` stops with the commit
  applied and amends what is staged on Continue.
- **Messages are committed verbatim** (`commit.cleanup=verbatim`) so no
  Git template or comment text can alter a reword, squash-chain, or
  fixup `-c` message byte for byte.
- **Stop snapshots:** the server records each stop's facts (HEAD, whether
  Git had already committed the step, emptiness) the first time one of its
  own commands observes it, since Git's own state files can't be
  re-derived reliably later (a prepare-commit-msg hook can change the
  message; a commit made in a terminal or just before a crash looks like
  progress). A stop no command observed is marked `Late` and refuses
  Continue/Skip where a guess could duplicate or drop a commit.
- **Server-owned edit stop after a conflict at an edit step:** Git itself
  does not stop again for editing once an `edit` step's pick needed
  resolving, so the server commits the resolution itself and presents the
  edit stop without writing Git's own state files.
- Every abort of an application rebase writes a backup ref
  (`refs/tui-go/rebase-backup/<operation>[-n]`) before it runs, so anything
  the server made at a stop stays recoverable; the application never
  deletes these refs.
- Driving Git requires **Git ≥ 2.38** (capability `git-rebase-interactive`);
  the plan validator (`protocol.ValidateRebasePlan`) is stricter than Git
  itself: a squash/fixup must directly follow a commit-producing entry
  (never a drop or break), and starting needs an explicit acknowledgement
  whenever any commit already published to a remote-tracking ref is in the
  rewritten range.
- **Fetch** refuses a remote whose configured refspec destination leaves
  `refs/remotes/<name>/` or overlaps another remote's namespace
  (`unsafe_refspec`, the other remotes are still fetched), and Fetch &
  prune always passes `--no-prune-tags` — tags are never pruned by either
  action.
- **Planning jobs take no writer lease.** A rebase-planning job pins the
  checkout (branch, HEAD, index, working-tree status, effective
  configuration, hooks, `info/`, refs) before each turn and compares it
  after, tainting the proposal on any difference rather than blocking other
  threads or Git writes for the whole planning turn.
- **Transport is structured text**, not a tool: the agent answers with one
  fenced `tui-rebase-plan` JSON block in its final message segment, parsed
  strictly (unknown fields, repeated keys, wrong case, `exec`, and
  out-of-parity actions are all errors) and validated against the pinned
  plan exactly like a manual plan.
- **Read-only modes on the built-in bridges** are used for planning jobs
  when the agent is a verified built-in bridge: Claude opens with
  `--permission-mode plan` and `useAutoModeDuringPlan: false`; Codex opens
  App Server v2 with `sandboxPolicy {"type":"readOnly","networkAccess":
  false}` and `approvalPolicy "never"`. This is **documented provider
  behaviour, not verified against a live account** — only against fake CLIs
  in this run (launch arguments, catalogue, refusals, the policy sent to
  App Server). Every agent, verified or not, still gets its approvals
  declined and the after-turn checkout comparison as defence in depth.

## Residual risks and known limits

From the ADR 0026/0027 "Known limits" sections:

- A server crash **between a stop commit and the journal** leaves that
  commit unrecorded: a retried Continue may make it again (only for a kept
  empty commit or a reworded amend), and Abort falls back to the backup ref
  rather than the journal to recover it.
- An **author-identity corner case**: the committed-step classification
  relies on Git keeping a step's original author (name, email, date); a
  previous result made in a terminal at an earlier stop with exactly the
  same author, date and change as the next step's commit would be taken
  for that step's commit. Do not run the server with `GIT_AUTHOR_*`
  overridden in its own environment — that defeats the test entirely.
- **Backup refs are never auto-deleted** by the application
  (`refs/tui-go/rebase-backup/...`); pruning them is a deferred decision
  (see "Next run" below).
- A **prepare-commit-msg hook's additions** are kept on steps whose message
  Git itself composes (pick) but replaced on steps whose message the
  helper writes (reword, the end of a squash chain, `fixup -c`, a resolved
  conflict) — the helper always writes the complete stored message.
- **Planning taint from terminals or other programs is not attributed** to
  anyone: the reason names what changed but never claims the agent did it,
  and a change made by the user in a terminal during a planning turn taints
  the proposal the same as an agent write would.
- **Submodule hooks** (`.git/modules/*/hooks`) and other parts of
  submodules' own Git directories are not pinned by the planning-job
  comparison.
- **Live provider behaviour is unverified**: both read-only bridge modes,
  the plan-transport parsing against a real agent's actual output shape,
  and the whole agent-planning flow have only run against fake ACP agents
  and fake CLIs.
- The **PTY harness doesn't cover agent planning** at all (see above); it
  covers fetch/prune, plan-editor reorder/squash/reword, soft reset, and an
  edit stop for the manual path only.
- **Planning forms and in-flight entries are never pruned for deleted
  threads.** `gitPl.forms`/`gitPl.sent` in the TUI keep an entry per Git
  target once touched, even after its job thread is deleted; this is
  in-memory client state only (never persisted, never shown to the user),
  but it is a small unbounded-growth leak for a long-lived TUI session.
